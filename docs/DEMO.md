# Demo Environment

A completely separate, fictional "Apex Corporation" instance of the Performance
Management System — safe to run publicly, screenshot, or hand to a recruiter/client. It
uses its own database, its own branding, and its own set of demo accounts. **It never
touches the real Development database** (see [Environments](../README.md#environments)
in the main README for how the three environments relate to each other).

## Quick start

```bash
# 1. Start the demo Postgres container (separate from the Development one)
docker compose up -d postgres-demo

# 2. Seed it with deterministic, entirely fictional data (~200 employees, 3 review years,
#    every workflow stage represented, all 6 Workflow Administration actions exercised)
dotnet run --project src/PerformanceManagement.DemoSeeder

# 3. Run the app against it
ASPNETCORE_ENVIRONMENT=Demo dotnet run --project src/PerformanceManagement.Web --no-launch-profile --urls https://localhost:5275
```

`--no-launch-profile` matters: the project's `launchSettings.json` default profile
hardcodes `ASPNETCORE_ENVIRONMENT=Development`, which otherwise silently overrides the
`ASPNETCORE_ENVIRONMENT=Demo` you just set.

**Demo requires HTTPS to actually work** — by design, Demo is configured to behave exactly
like a real deployed instance (secure cookies, HSTS, strict antiforgery), not a relaxed
local-dev mode. Over plain HTTP it will refuse to render any page with a form (an
`AntiforgeryOptions.Cookie.SecurePolicy = Always` check fails loudly rather than silently
degrading). For local testing, trust a dev certificate once:

```bash
dotnet dev-certs https --trust
```

then use an `https://` URL as shown above. In the real VPS deployment, a reverse proxy in
front of Kestrel terminates TLS the same way; no code change is needed for that case.

## One-command reset

```bash
./scripts/reset-demo.sh
```

Stops the demo Postgres container, deletes its volume entirely (a genuinely fresh
database, not just a table wipe), starts a new one, and reseeds. Never touches the
Development container/volume — they have different names entirely.

## Demo login credentials

| Role | Username | Password |
|---|---|---|
| HR Administrator | `admin` | `Admin@123` |
| Manager | `manager` | `Demo@123` |
| Employee | `employee` | `Demo@123` |

Every other seeded employee also has a login: the employee's 4-digit code as the
username, `Demo@123` as the password (mirrors the same per-employee login pattern the real
Development environment uses).

The `manager`/`employee` pair is deliberately a real, related manager → direct-report pair
in the seeded org chart, so logging in as either one immediately shows a populated,
genuinely-linked PM Form rather than an empty state.

## What's in the seeded data

Generated by `PerformanceManagement.DemoSeeder` (`src/PerformanceManagement.DemoSeeder/`),
fully deterministic — the same fixed random seed always produces byte-identical data, so
screenshots, documentation, and bug reports stay reproducible:

- 15 fictional departments, 5 job families, 4 rating bands (Outstanding / Very Good / Good
  / Needs Improvement), 18 KPIs and 12 competencies spanning all perspectives/types.
- ~200 employees with multi-national names across a believable ~2-level org chart (5
  executives, 30 department managers, ~165 staff).
- Three review years (2024, 2025, 2026) — 2024/2025 are fully closed ("Completed") cycles
  so Reports show genuine year-over-year trend data; 2026 has a realistic mixed-status
  distribution (70% Completed, 10% HR Review, 7% Mid-Year, 5% Draft, 5% Returned, 3%
  Reopened) rather than everything uniformly finished.
- All 6 Workflow Administration actions (Return to Employee, Return to Manager, Reopen
  Review, Resend Notification, Administrative Completion, Unlock Review) exercised for
  real via `WorkflowAdminService`, so the Workflow Administration console and Audit
  History have genuine, non-fabricated entries to show.
- Every PM form is driven through the real `WorkflowService`, not raw row inserts — the
  same validation, scoring, and audit trail as a real user would produce.
- Demo never sends real email: no SMTP host is configured for it, so every dispatch is
  logged (`EmailLog`), never actually sent.

## Recreating the demo database

Either re-run the seeder against a still-empty demo database, or use `--reset` to wipe and
reseed an existing one:

```bash
dotnet run --project src/PerformanceManagement.DemoSeeder -- --reset
```

The seeder refuses to run against the real Development connection string/port (5445)
unless `--force-unsafe` is explicitly passed — an extra guard on top of the different
default connection, protecting the real database from ever being touched by this tool.
